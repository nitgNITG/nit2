## 1. Executive Summary

ختمة (Khatma) هي منصة ويب لختم القرآن الكريم بشكل جماعي أو فردي. تتيح للمستخدمين إنشاء ختمات، حجز الأجزاء، تتبع التقدم، والتفاعل مع مجموعات قرآنية منظمة. الهدف الأساسي هو تيسير تجربة الختم الجماعي بشكل رقمي آمن وفوري.

**Target Users:** المسلمون الراغبون في ختم القرآن بشكل فردي أو ضمن مجموعات عائلية أو اجتماعية.

**Core Value Proposition:** "اختم القرآن مع من تحب في أي وقت ومن أي مكان."

---

## 2. Problem Statement

### المشكلة الحالية
- يتم تنظيم الختمات الجماعية حالياً عبر WhatsApp أو يدوياً مما يؤدي إلى:
  - تعارض في حجز الأجزاء
  - عدم وضوح التقدم الفعلي
  - صعوبة إدارة المجموعات الكبيرة
  - فقدان السجل والأرشيف
  - غياب التحفيز والإشعارات الذكية

### الحل
منصة متكاملة تعالج هذه المشاكل بـ:
- حجز فوري بدون تعارض (Optimistic + DB-level locking)
- تحديث لحظي لجميع المشاركين (WebSockets)
- إدارة مجموعات متقدمة
- لوحة تقدم بصرية جذابة

## 4. Non-Functional Requirements

### NFR-001: Performance
| ID | Metric | Target |
|----|--------|--------|
| NFR-001-1 | وقت استجابة API (p95) | < 200ms |
| NFR-001-2 | وقت تحميل الصفحة (LCP) | < 2.5s |
| NFR-001-3 | تأخر الـWebSocket | < 100ms |
| NFR-001-4 | معدل الطلبات المدعومة | 10,000 req/min |
| NFR-001-5 | المستخدمون المتزامنون | 50,000+ |

### NFR-002: Reliability
| ID | Metric | Target |
|----|--------|--------|
| NFR-002-1 | Uptime | 99.9% |
| NFR-002-2 | MTTR (Mean Time To Recovery) | < 30 min |
| NFR-002-3 | RPO (Recovery Point Objective) | < 1 hour |
| NFR-002-4 | RTO (Recovery Time Objective) | < 2 hours |

### NFR-003: Security
- HTTPS فقط (HSTS)
- JWT + Refresh Token Rotation
- Rate Limiting على كل نقطة API
- Input Sanitization و Validation
- SQL Injection Protection (Prisma ORM)
- XSS Protection (CSP Headers)
- CSRF Protection

### NFR-004: Scalability
- Horizontal Scaling للـBackend
- Redis للـCaching و Session
- Database Read Replicas
- CDN للأصول الثابتة

### NFR-005: Accessibility & UX
- RTL عربي كامل
- دعم شاشات 320px → 2560px
- تباين ألوان WCAG 2.1 AA
- دعم قارئات الشاشة

### NFR-006: SEO
- SSR / ISR لجميع الصفحات العامة
- Open Graph + Twitter Cards
- Structured Data (Schema.org)
- Sitemap ديناميكي
- Core Web Vitals جيدة

## 5. User Personas

### Persona 1: أم علي — الأم المنظِّمة (40 سنة)
- **الهدف:** تنظيم ختمة عائلية في رمضان
- **التحديات:** لا تتقن التقنية كثيراً، تريد بساطة
- **الاحتياجات:** واجهة بسيطة، مشاركة رابط للعائلة، رؤية تقدم كل فرد

### Persona 2: أحمد — الشاب المتدين (25 سنة)
- **الهدف:** المشاركة في ختمات متعددة مع الأصدقاء
- **التحديات:** مشغول، يحتاج تذكيرات
- **الاحتياجات:** تطبيق سريع، إشعارات ذكية، واجهة عصرية

### Persona 3: الشيخ محمد — إمام المسجد (55 سنة)
- **الهدف:** إدارة ختمات المسجد للمجتمع
- **التحديات:** مجموعة كبيرة، احتياج لإدارة متقدمة
- **الاحتياجات:** إدارة مجموعات، تقارير، صلاحيات

### Persona 4: فاطمة — المديرة التنفيذية (35 سنة)
- **الهدف:** ختمة فردية منتظمة
- **التحديات:** وقت محدود، تريد تتبع تقدمها
- **الاحتياجات:** ختمة فردية، إحصائيات، تحفيز

## 6. Acceptance Criteria (Core Features)

### AC-001: حجز الجزء
```
GIVEN مستخدم مسجل في ختمة
WHEN يحاول حجز جزء متاح
THEN يتم الحجز فورياً
AND تتغير حالة الجزء إلى "محجوز" لجميع المستخدمين
AND لا يستطيع مستخدم آخر حجز نفس الجزء
AND يظهر اسم الحاجز بجانب الجزء
```

### AC-002: منع التعارض
```
GIVEN مستخدمان يحاولان حجز نفس الجزء في نفس اللحظة
WHEN يُرسَل الطلبان في نفس الوقت
THEN يحجز المستخدم الأول
AND يتلقى الثاني رسالة خطأ "الجزء محجوز"
AND لا تتأثر بيانات الـDB بالتعارض
```

### AC-003: التحديث الفوري
```
GIVEN مستخدمان يشاهدان نفس الختمة
WHEN يحجز أحدهما جزءاً
THEN يرى الآخر التغيير خلال 500ms بدون إعادة تحميل
```
